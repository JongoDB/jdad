## High findings

### H1. `main` can't be protected, and everything deploys from it

- **Evidence.**
  - `gh api repos/JongoDB/jdad/branches/main/protection` returns 403: "Upgrade to GitHub Pro or make this repository public to enable this feature." The rulesets endpoint returns the same.
  - `gh api repos/JongoDB/jdad/collaborators` lists one account, `JongoDB`, as admin. PRs #1 to #4 were all opened and merged by `JongoDB`. This session's own `gh` credential is that admin account.
  - `deploy/update-docker.sh:224` deploys whatever `git pull --ff-only` brings in. `.claude-plugin/marketplace.json:11` has `"source": "./"`, so the plugin is whatever `main` holds.
  - `ROADMAP.md:49` and `ROADMAP.md:219` make branch protection a prerequisite for bot KB PRs and for auto-update, and name that same `gh api` call as the evidence.
- **Impact.** Any agent session on any of Jon's hosts can push to `main` by mistake or under prompt injection. The next `update-docker.sh` run then serves it to every agent, and once marketplace auto-update is on (already approved), the plugin's commands and skills install on every host. "Nobody merges their own PR" is policy only. The two roadmap prerequisites can't be met as written, so P1.3's bot PRs and P7.2 are blocked without anyone having noticed.
- **Fix.**
  1. Jon picks one: GitHub Pro for the account, or make the repo public (see R7 for what public needs first).
  2. Add a ruleset on `main`: PR required, no force push, no deletion, applies to admins, `verify` check required once H2 is fixed.
  3. Give bots their own identity (a machine user or a GitHub App) with no bypass rights, so "required approval" becomes possible.
  4. Until then: keep auto-update off, and have the droplet deploy a named tag or SHA that Daisy chooses, not the head of `main`.

### H2. CI never runs

*(Corrected; see Errata. The macOS `./verify` problems first listed here are now M10.)*

- **Evidence.**
  - `gh run list`: every run on every PR and on `main` is `failure` after 2 to 3 seconds (the known billing block, `README.md:390`).
  - `verify:37-42` skips `claude plugin validate` when the CLI is missing, which is always the case in CI.
  - There is no `.python-version`. `uv run` here picked CPython 3.14.7, while the image uses 3.12.
  - `./verify` itself is green on Linux (Checker, PR #6 review). It fails on macOS for reasons of its own (M10).
- **Impact.** No PR has an automated gate. Every PR's proof is the author's own report of a local run, checked by a reviewer who has to rerun it. With H1 (no branch protection), nothing technical stops a red change from merging. The fix for CI sits in P5.1, behind Phase 1 to 4.
- **Fix.**
  1. Fix Actions billing now (Jon approved it on 2026-11-22), or make the repo public (Jon decided this on 2026-11-22), which makes Actions free.
  2. Add `.python-version` (3.12) so local, CI and image agree.
  3. Install the `claude` CLI in CI, or make a skipped plugin validation fail on CI.
  4. Make `verify` a required status check once it runs (H1).

### H3. The origin is open to the internet

- **Evidence.**
  - `docs/evidence/p0.5/droplet.txt:6`, `:22` and `:38-39`: the container publishes `0.0.0.0:443` and `[::]:443`. Brief 01 says there is no DigitalOcean cloud firewall; I couldn't check that (unverified, see Errata). Either way the host itself accepts 443 from every address.
  - Probe: `GET /healthz` with `Host: evil.example.com` returns 200. `/healthz` isn't covered by the Host allowlist.
  - `droplet.txt:52`: the origin certificate's SAN is `*.jondevs.com, jondevs.com`. Anyone who scans the IP range gets a certificate that names Jon's zone, which is the usual way origins behind Cloudflare are found.
  - `droplet.txt:64`: the origin answers `server: uvicorn`.
  - `ROADMAP.md:104` says Jon has no DigitalOcean console access (support ticket open), so the firewall in `README.md:191-200` can't be created yet. The firewall isn't a roadmap item.
- **Impact.** Requests sent straight to the IP skip Cloudflare, so the rate limiting and WAF planned in P5.6 would not apply to an attacker. A single uvicorn process doing its own TLS on one vCPU is exposed to scanners and slow-connection attacks. The bearer token is the only control. Confidentiality isn't at risk; availability for every agent is.
- **Fix.**
  1. Now, without the console: on the droplet, add rules to the `DOCKER-USER` iptables and ip6tables chain that accept TCP 443 only from Cloudflare's published ranges and drop the rest, and persist them. Docker-published ports bypass ufw but not `DOCKER-USER`. This needs SSH only.
  2. When console access returns: the DigitalOcean cloud firewall from the README.
  3. Later: Authenticated Origin Pulls.
  - Acceptance: from a host outside Cloudflare, a TCP connect to the origin IP on 443 times out over IPv4 and IPv6; the public URL still returns 200 on `/healthz`.

### H4. KB text reaches every agent as instructions, with no defence against poisoning

- **Evidence.**
  - `src/jdad/server.py:32-37` tells agents to call the KB before planning and to follow and cite its rules. `commands/jdad.md` and the `apply-kb` prompt do the same.
  - `sources/` holds third-party text "verbatim" (`CLAUDE.md`, step 2) and `get_source` returns it unmarked.
  - Jon approved bots opening KB PRs (`ROADMAP.md:50`). With H1 and H2, a KB PR has no technical gate.
  - Probe: with `KB_ROOT` unset, `resolve_kb_root()` run from an unrelated directory tree that happened to contain `practices/` and `sources/` served that tree as the KB (`src/jdad/kb.py:34-37` walks up from the current directory first).
  - No roadmap item covers this. P1.2 and P1.3 lint structure, not content.
- **Impact.** One hostile line, from a video description, an article, or a compromised bot session, becomes a "rule" that agents apply in every repo Jon works in. A stdio server started inside another project can also serve that project's files as Jon's KB.
- **Fix.**
  1. `resolve_kb_root`: stop walking up from the current directory. Use `KB_ROOT`, then the package's own checkout, then bundled data.
  2. Mark `get_source` output as quoted third-party material in the tool description and in a one-line header on the result.
  3. Extend `jdad lint-kb` (P1.2, P1.3): fail on text addressed to an agent ("ignore", "run", "curl … | sh" patterns), on URLs or shell commands in `practices/` outside an allowlist, on hidden or bidirectional Unicode, on HTML comments, and on symlinks.
  4. Require a human approval on changes under `practices/` (CODEOWNERS, once H1 allows it).
  5. Add one poisoned-source task to the eval set (P6.1).
